## 0. How the agent must use this plan
1. Read this file top to bottom, then `AGENTS.md`, then the parent plan, then `restyle-v3-audit/ISSUES.md`.
2. Work one slice at a time, in order. Do not start a slice before the previous one is committed, pushed and handed off.
3. For every slice, before editing, write a SPEC SHEET (template in section 3) into the PR notes (not committed). The mock HTML is the spec: its values are inline styles you can read. The mock PNG next to it shows the same screen.
4. If anything in a slice is unclear, contradicts the mock, or needs a backend change, STOP and ask. Never guess. Never decide a product question (check `docs/project-context/06-open-questions.md` first).
5. After every slice: build, run the named specs, light AND dark check at 1440 width, commit with prefix `ui(v3):`, push, write the 5-line handoff (section 9).
6. Anything marked VERIFY IN MOCK means the plan author did not read that part of the mock. Read it and follow the mock; report any mismatch with this plan.

## 2. Hard rules (apply to every slice)
R1. Do not touch: login page and `login.css`; backend (`be/`); migrations; `docs/project-context/`; `.github/`. `git diff main -- fe/src/partials/shell/login* fe/src/styles/modules/login.css` must be empty.
R2. Preserve every DOM id, `data-*` hook, `onclick` target, route and function name that JS or tests use. If you must move an element, keep its id and its event wiring.
R3. Behaviour is frozen. Same API calls, same arguments, same permission checks, same validation, same state transitions. Visual and structural changes only.
R4. Payroll policy: internal estimate, portal-confirmed amount, actual paid amount and variance stay separate and separately labelled. Missing employee bank details stay a visible flag and never block. Keep 'Employee bank account' vs 'Company account' wording. HRFlow is not the statutory calculator.
R5. Styling: Finance v2 system through `.fv` scope and tokens in `tokens.css`. No colour literals in partials, in `app-v3.css`, `hr-v3.css`, `payroll-v3.css` or JS (use `var(--...)`). Run `npm run lint:finance-tokens` in `fe/`. Do not restyle global `.btn`, `.badge`, `.card`, `.filter-tab`; use `.fv`-scoped rules.
R6. Sentence-case headers and labels. No uppercase section labels. No '...' row menus. Row actions: at most one text button plus three icon buttons.
R7. Feature parity by mock (D5): every control on a screen must either (a) appear in the mock, or (b) be an existing real feature the mock does not show. Controls added by the earlier pass that are in neither group are removed. A control that exists but does nothing is a bug: wire it to a real function or remove it.
R8. Real-only features stay (for example Notes on employee detail). Style them in the same system and place them after the sections the mock shows.
R9. Mock data is never copied into real screens. Mock files are styling and structure references.
R10. Light AND dark must both look right (navy palette from the parent plan section 3.2). Forbidden near-black values `#0f1117 #171a24 #1d2130 #2a2e3d #23273a` must not appear in any dark rule: `grep -rn` them after each slice.
R11. Existing tests: update a spec only where it asserts wording or markup this plan deliberately changes. Never weaken a test to make it pass; say in the handoff what changed and why. Add a conformance assertion for each slice (section 8).
R12. No new dependencies, no framework, no build changes.
R13. Never commit screenshots, traces, temp scripts or test output. Save screenshots outside the repo (for example the OS temp folder) and cite the path in the PR notes.
R14. Use `npm run build` in `fe/` before any Playwright run (tests run against `fe/dist`). Targeted specs during work; the full suite once at the end of each phase.
R15. Token efficiency (AGENTS.md): no polling loops, compact reporters (`--reporter=line`), `git diff --stat`, never bare `git diff`.
R16. Labels (D2): every slice has a LABEL TABLE. Any visible text not in the table follows the mock exactly. Any text in the table marked 'kept' keeps the real wording and is repeated in the handoff.
R17. Static arrows (D3): the only sort indicator allowed is a static arrow on a column the app already orders by. No `onclick`, no `role=button`, no pointer cursor.
